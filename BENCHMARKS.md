# Benchmarks

**Every number in this document was measured, not estimated.** Source:
`benchmark/results.json`, generated by `benchmark/run.js` against real live
pages, a real local Playwright browser render, and a real NIM API. No
extrapolated or assumed figures.

Last measured: 2026-08-12T23:50Z, model `nvidia/llama-3.3-nemotron-super-49b-v1`.

## What kind of test each case is

- **Deterministic local tests** (`test/`, `npm test`) — fixture-based, zero
  network, run in CI on every push. Not this document's subject.
- **Live validation + benchmark** (this document, `benchmark/`) — real
  external pages, a real Playwright browser render (against a local fixture,
  not an external site — see the SPA case below for why), and real LLM
  calls. Costs time and API usage. Not run in CI (see `.github/workflows/test.yml`).

## Results — 8 cases, genuinely different page architectures

| Case | Tier | LLM | Browser | Items | Confidence | Latency | Result |
|---|---|---|---|---|---|---|---|
| Zomato restaurant metadata (relevant JSON-LD) | `json-ld` | no | no | 1 | 0.95 | 918ms | ✅ |
| Zomato reviews (irrelevant JSON-LD present, correctly skipped) | `hydration` | yes | no | 5 | 0.75 | 32,878ms | ✅ |
| DigitalOcean tutorials (Next.js `__NEXT_DATA__`, different domain) | `hydration` | yes | no | 9 | 0.75 | 31,650ms | ✅ |
| example.com (plain SSR, no structure, single entity) | `text` | yes | no | 1 | 0.50 | 1,513ms | ✅ |
| books.toscrape.com (e-commerce product, no JSON-LD) | `text` | yes | no | 1 | 0.50 | 4,923ms | ✅ |
| quotes.toscrape.com (text content, list of 10 items) | `text` | yes | no | 10 | 0.50 | 17,864ms | ✅ |
| Honest-failure case (schema asks for data the page doesn't have) | `text` | yes | no | **0** | 0 | 848ms | ✅ (correctly empty, no hallucination) |
| SPA shell requiring browser rendering (local fixture + real Playwright) | `text` | yes | **yes** | 1 | 0.50 | 5,348ms | ✅ |

**8/8 passed** — where "passed" for the honest-failure case specifically
means *correctly returning nothing*, not extracting a plausible-looking
fabrication. See "Why the honest-failure case matters" below.

**1 of 8 avoided the LLM entirely** (the JSON-LD case — the only page in
this corpus that had schema.org data actually matching what was asked for).
**JSON-LD is ~35x faster than the LLM-backed tiers** in this run (918ms vs.
an ~32,000ms average for the two hydration cases) — the concrete cost of a
page not exposing structured data for what you want.

## Why the honest-failure case matters

A schema asking for `productSku`, `warehouseLocation`, and
`supplierContactEmail` was run against example.com — a page that obviously
has none of that. The correct result is zero items, not a fabricated
plausible-sounding answer. This is a **known past failure mode of the
default LLM prompt** (see "Bugs found" below) — earlier in development,
single-entity pages sometimes returned an empty array *even when they did
have relevant data*, which risked overcorrection in the other direction
(fabricating data that isn't there, to avoid returning empty). This case
exists specifically to catch that regression. It didn't happen.

## Why the SPA-rendering case uses a local fixture, not a live external site

Real browser-rendering was verified with a **real Playwright Chromium
instance actually launching and rendering a page** — this is genuine live
validation of `renderWithBrowser`, `extraction.browserUsed`, and the
`needsBrowser` detection heuristic, not a synthetic unit test. It targets a
local fixture (`benchmark/fixtures/spa-product.html` served over real HTTP
via `benchmark/local-server.js`) rather than an external SPA site, so this
specific check doesn't silently break because some third-party site changed
its markup or went down — the thing being tested is *our* browser-rendering
path, not any particular external site's stability.

## Next.js hydration: a real finding, not just a checkbox

`nextjs.org` itself — and several other well-known sites checked during
this work — **no longer use the classic `__NEXT_DATA__` pattern**, almost
certainly because they've moved to the App Router (React Server Components
streaming) rather than the older Pages Router convention this project
detects. DigitalOcean's tutorials page (`community/tutorials`) was found to
still use it and was added to the corpus specifically because it's a real,
different domain than every other case here — not cherry-picked for being
easy.

## Bugs found and fixed via real testing, not left as known issues

1. **Deeply nested hydration state silently missed present data.** The
   Zomato hydration case initially returned 0 items despite the data being
   confirmed present. Fixed generically (not Zomato-specific) in
   `extraction/auto.js` with an instruction to search nested structure.
2. **Single-entity pages returned an empty array.** Fixed in
   `extraction/llm.js`'s default system prompt. The honest-failure case
   above exists to make sure this fix didn't overcorrect into fabrication.
3. **The tier-1 relevance heuristic had a false-positive on small schemas.**
   A 2-field schema sharing one common field name (e.g. `name`) with an
   unrelated block was wrongly accepted. Fixed in `extraction/json-ld.js`
   by returning only the top-scoring block(s), not everything above a
   floor — caught by a committed test before reaching a live run.
4. **`needsBrowser` in the result didn't tell you whether a browser was
   actually used.** `auto.js` re-classifies the *rendered* HTML after a
   browser render, so `needsBrowser` in the final result reflects
   post-render state (usually `false`, since real content now exists) —
   correct for "would a fresh fetch need a browser," but useless for "was a
   browser used for this specific extraction." Added `extraction.browserUsed`
   as a separate field. Found while building the SPA-rendering benchmark
   case itself, not anticipated in advance.

All four fixes are default behavior now, not something you need to
configure.

## Known gaps — still not covered

- **React/SPA rendering was validated with a local fixture, not a live
  external SPA.** The mechanism is proven; a live external example would
  add real-world confidence on top of that, not change the mechanism.
- **8 cases is a real, diverse corpus, not a token one — but it is not the
  10-20 case target** a mature benchmark should reach. Grow it further
  before treating any percentage derived from this data as broadly
  representative of "the web."
- **No article/news page with `Article`-typed JSON-LD** — quotes.toscrape.com
  covers text-shaped content but has no structured markup at all; a page
  with relevant-but-different-typed JSON-LD (e.g. `Article` instead of
  `Review`/`Restaurant`/`Product`) hasn't been tested.
- **No infinite-scroll/lazy-load page** — `core/pagination.js`'s
  termination strategies are unit-tested (`test/pagination.test.js`) but
  not exercised against a real infinite-scroll page in this benchmark
  (that's more naturally an adapter-level concern — see `ADAPTERS.md` —
  than something `autoExtract`'s single-page model handles).

**Do not repeat unqualified claims like "X% of pages skip the LLM" from
this data alone** — 8 samples, while genuinely diverse, is still a modest
corpus. The claim this data actually supports: *"across 8 genuinely
different page architectures, the engine correctly identified which tier
could answer each request, used JSON-LD when — and only when — it was
actually relevant, correctly declined to fabricate data that wasn't
present, and correctly used real browser rendering when required."*

## Running this yourself

```bash
NIM_API_KEY=your-key node benchmark/run.js
```

Requires `npm install` (pulls in `playwright` and `undici`, both optional
dependencies of the base package) and `npx playwright install chromium` for
the browser-rendering case. Not part of `npm test` — see `CONTRIBUTING.md`.

## Expanding this corpus

`benchmark/corpus.js` is a plain array — add a case with `{ name, url,
schema, options, expectMinItems, ... }` (see existing entries and
`run.js`'s `checkExpectations` for the available expectation fields,
including `isHonestFailureCase` and `expectBrowserUsed`) and re-run.
Contributions that add real, diverse, verified cases (especially the gaps
listed above) are more valuable right now than additional features.
